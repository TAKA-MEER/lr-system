# LRシステム 第2期評価試験計画(限界特性試験)

作成日: 2026-09-27
対象: `app/` 一式(faster-whisper large-v3 + VAD / BT-RMS話者判定 / qwen3.5:9b 2段階議事録生成)
前提となる過去試験: `testing/CHANGELOG.md`(script_v1 短時間試験 × 約20run、3時間耐久 × 3run)

---

## 0. 背景と狙い

これまでの試験は次の点で条件が「きれいすぎる」ため、実運用での限界が分かっていない。

| これまでの条件 | 実運用で起こりうること |
| --- | --- |
| 合成音声をデジタルのまま無劣化で注入 | 工場騒音・残響・マイク距離・BT(HFP)帯域制限・クリップ |
| 4話者・4声・読み上げ速度ほぼ一定 | 5〜8名、早口/遅口、小声、声質の似た話者 |
| ターンは交互・重なりなし・0.4〜0.9秒の間 | 相槌、割り込み、同時発話、1〜2秒の早い応酬 |
| 題材は配電盤1種類のみ、協議事項7〜11件 | 変圧器・回転機・制御盤など他機種、協議事項20件超 |
| BTにはBT装着者の声だけが入る(漏れ込みゼロ) | 相手方の声がBTマイクに漏れ込む、装着者が小声 |
| 毎runの前にコンテナを再起動 | 再起動しないで連続試験、ブラウザのリロード、再接続 |
| 正常系の操作のみ | 録音中の生成ボタン押下、二重押下、Ollama停止、コンテナ落ち |

本計画では **要因を1つずつ段階的に悪化させて、どこで品質が許容値を割るか(限界点)を測る** ことを主眼とする。
そのうえで、判明した限界に対して改善を行い、同じ試験で効果を確認する。

## 0.5 試験環境と実機の違い(ノートPCの模擬)

| | 試験環境(本PC) | 実運用機 |
| --- | --- | --- |
| 形態 | デスクトップ | ノートPC |
| CPU | Core i7-13700F(16コア/24スレッド) | ノート向けCPU(コア数・クロックとも低い想定) |
| RAM | 32GB | **16GB**(README推奨のとおりWSL2に12GBを割り当てる場合、Windows+Chrome 2窓は残り約4GBで動く) |
| GPU | VRAM 8GB(過去試験の実測で8188MiB) | **VRAM 8GB**。ノート向けGPUは電力上限が低く、発熱で性能が下がる |
| 現在の `.wslconfig` | `networkingMode=mirrored` のみ(メモリ上限なし) | README推奨 `memory=12GB` |

VRAM容量は同じなので、VRAMが足りるかどうかの結果はそのまま使える。一方、**処理速度とRAMは本PCの方が余裕があるため、そのまま試験すると実機より良い結果が出る**。そこで次のように実機に近づける。

1. **RAMの制限**: 試験中は `.wslconfig` を `memory=12GB` にし、Windows側でも Chrome 2窓を開いた状態で試験する(L2・L3)。コンテナのメモリ使用量とWindows全体の空きメモリを記録し、16GB機で足りるかを判断する。
2. **CPUの制限**: `.wslconfig` の `processors` や docker の `cpus` で使えるコア数を 8 / 4 に絞って試験する(ffmpeg変換・Opusデコードは CPU で動く)。
3. **GPU速度の模擬**: 管理者権限が使えないため電力上限の変更は行わない。代わりに D-2(注入を 1.5〜3 倍速にする試験)で「処理速度が何割落ちても間に合うか」という余裕として評価する。
4. **VRAMの残量**: ノートPCでは画面表示にもGPUを使う(外部モニター接続時は特に)ため、D-3 で 0.5〜1.5GB を先に使った状態でも動くかを確認する。
5. **長時間の発熱**: 本PCでは再現できないため、最後に**実機ノートPCで短時間試験(script_v1)と1時間試験を1回ずつ行う**ことを推奨する(合成音声の注入スクリプトはそのまま実機で動かせる)。

これに合わせて D群に次を追加する。

- D-6: RAM 12GB(WSL)+ Chrome 2窓での長時間試験で、スワップ発生・メモリ不足による停止がないか
- D-7: CPU 4コア制限時のSTT遅延・ffmpeg変換時間

## 1. 試験の層構成

実時間注入(1時間の音声 = 1時間の試験)だけでは条件数を増やせないため、3層に分ける。

| 層 | 方法 | 用途 | 所要時間の目安 |
| --- | --- | --- | --- |
| **L1 コンポーネント試験** | `docker exec` でコンテナ内の `Transcriber` / `SpeakerDetector` / Stage1・Stage2 を直接呼ぶ。音声は本番と同じ WebM/Opus 5秒チャンクに切ってから渡す | 条件を大量に振る掃引(音響・話者判定・LLM入力) | 非実時間。STTはRTF 0.1〜0.2程度を想定 |
| **L2 E2E試験** | 既存の `inject/run_injection.py` で2本のWebSocketに実時間注入 → 生成 → 評価 | L1で見つけた限界付近の代表条件を本番経路で確認 | 音声尺 + 生成時間 |
| **L3 異常系試験** | WebSocket/RESTを直接叩くスクリプトで操作順序・障害を注入 | 運用上の誤操作・障害時の挙動(データ消失の有無) | 1ケース数分 |

L1で得た限界点がL2でも再現することを確認して、L1の結果を「本番相当」とみなせるようにする。

## 2. 試験用データの作り方(合成音声)

### 2.1 音声合成

- VOICEVOX Engine(CPU版、既存と同じ)を使う。
- 声の種類を 4 → **10声程度**に増やす(男女・年齢感・声の高さが違うもの、ささやき等のスタイルも含む)。
  追加する声は、クレジット表記のみで商用・非商用とも制限のないキャラクターを優先して選び、`CREDITS.md` に追記する。
  (既存の青山龍星は企業が関わる利用で事前確認が必要なため、新規台本では使わない)
- 発話ごとに `speedScale`(0.8〜1.6)、`pitchScale`、`intonationScale`、`volumeScale` を台本から指定できるようにする。

### 2.2 音響劣化(新規 `testing/augment/`)

すべて numpy / scipy で合成し、外部データセットはダウンロードしない(オフライン前提と再現性のため。乱数シード固定)。

| 劣化要因 | 作り方 | 振る水準 |
| --- | --- | --- |
| 定常騒音(工場) | モーター/変圧器のハム(50/60Hz と 100/120Hz 高調波)+ ファン(帯域ノイズ)+ ピンク/ブラウンノイズ | SNR 30 / 20 / 15 / 10 / 5 / 0 dB |
| 衝撃音 | 打撃音・リレー動作音・遮断器投入音(減衰インパルス) | 毎分 0 / 6 / 30 回 |
| 警報音 | ブザー・ビープ(1〜3kHz正弦波の断続) | 有 / 無 |
| バブル(周囲の人の声) | 本題と無関係な台本を別の声で合成し、複数重ねる | 人数 0 / 2 / 4、SNR 15 / 10 / 5 dB |
| 残響 | 指数減衰ノイズによる合成インパルス応答 | RT60 0.3 / 0.8 / 1.5 秒 |
| マイク距離(音量) | ゲイン | 0 / −10 / −20 / −30 dB |
| クリップ | 入力を過大にして飽和 | 有 / 無 |
| BT(HFP)帯域制限 | 8kHz(狭帯域)と16kHz(広帯域)にリサンプル + 帯域通過 | 48k / 16k / 8k |
| BT音途切れ | 20〜200msの区間をランダムに無音化 | 0 / 1 / 5 % |

### 2.3 台本(新規 `testing/scenario/`)

既存の `script_v1.yaml`(配電盤)に加えて、題材と会話の形を変えた台本を用意する。すべて正解データ(`expected_*.yaml`)を人手で作る。

| ID | 題材 | 尺 | 主な狙い |
| --- | --- | --- | --- |
| S-TR | 油入変圧器 工場立会(変圧比・無負荷損・温度上昇) | 約15分 | 別機種への汎化、数値・単位の多い会話 |
| S-MT | 高圧電動機 工場立会(振動・騒音・効率) | 約15分 | 別機種、英字略語(IE3、JIS等) |
| S-PLC | 制御盤 ソフトウェアFAT(シーケンス・画面・I/O) | 約15分 | 専門用語の種類が違う、不具合指摘が多い |
| S-MULTI | 6〜8名参加(相手方3〜4、自社3〜4) | 約15分 | 話者数の限界、似た声の話者 |
| S-FAST | 1〜2秒の早い応酬、相槌、割り込み、同時発話 | 約10分 | 5秒チャンクの話者判定の限界 |
| S-STATUS | 状態が何度も変わる協議(合意→撤回→再協議→合意、保留→条件付き合意など) | 約15分 | 状態統合ルールの限界 |
| S-NOISE-TALK | 雑談・脱線・電話対応・関係ない話を多く含む | 約15分 | 議事録に不要な話が混入しないか |

加えて、L1のLLM試験用に**テキストだけの合成文字起こし**を作る(音声は作らない)。協議事項数・長さを自由に変えるため。

## 3. 試験項目

### A. 文字起こし(STT)の音響限界 — 主にL1

評価指標: CER(全体)、**数値・単位・型式の正解率**(`3.2メグオーム`、`AC2000V`、`SWB-2200` など議事録で重要な語を別集計)、専門用語正解率、無音・騒音区間での**ハルシネーション文字数**、処理時間(RTF)。

| No. | 試験 | 振る要因 | 知りたいこと |
| --- | --- | --- | --- |
| A-1 | 騒音SNR掃引 | 定常騒音 SNR 30→0dB | CERが0.20/0.30を超えるSNR |
| A-2 | 騒音種別 | 定常 / 衝撃 / 警報 / バブル(各SNR 3水準) | どの騒音に弱いか |
| A-3 | 残響 | RT60 3水準 × SNR 2水準 | 広い試験場での劣化 |
| A-4 | 音量・距離 | −30〜0dB、クリップ | 話者がマイクから遠い場合の限界 |
| A-5 | 話速 | speedScale 0.8〜1.6 | 早口の限界 |
| A-6 | 声質 | 10声 × 同一文 | 声による精度のばらつき |
| A-7 | 数値・専門用語 | 数値・単位・型式・英字略語を大量に含む文 | 議事録の正確性に直結する語の誤り率 |
| A-8 | 発話長とチャンク境界 | 1〜60秒の連続発話 | 5秒区切りで文が切れることによる誤り(既知課題の定量化) |
| A-9 | VAD設定 | `vad_enabled` × `vad_threshold` 0.05〜0.5 × 騒音 | 騒音時に発話が削られる/ゴミが出る境界、最適値 |
| A-10 | 長時間の騒音のみ区間 | 騒音だけが10〜30分続く | 騒音下でのハルシネーション(無音でのハルシネーションは対応済み) |

### B. 話者判定の限界 — L1(オフライン再現)+ L2

評価指標: 話者正解率(全体・発話長別・話者別)、our_side→client 誤り率、client→our_side 誤り率。

| No. | 試験 | 振る要因 | 知りたいこと |
| --- | --- | --- | --- |
| B-1 | BTへの漏れ込み | 相手方の声がBTマイクに −40 / −30 / −20 / −10dB で混入 | 固定閾値800で誤判定が始まる漏れ込み量 |
| B-2 | 装着者の声量 | 装着者の音量 −20〜0dB、ささやき | 小声だとclientと誤判定される境界 |
| B-3 | BT側の騒音 | BTマイクにも工場騒音(SNR掃引) | 騒音のRMSだけで閾値を超えてしまう境界 |
| B-4 | 発話の短さ | 1 / 2 / 3 / 5 / 10 秒ターン | 5秒チャンク単位で判定する方式の限界(1チャンクに2話者が入る割合) |
| B-5 | 時刻ずれ | BTストリームを 0 / 0.5 / 1 / 2 / 3秒 遅らせる・進める | BTとinternalの到着時刻差にどこまで耐えるか |
| B-6 | 閾値感度 | 閾値 200〜3000 × B-1〜B-3 の条件 | 条件ごとの最適閾値と、全条件で使える閾値が存在するか |
| B-7 | BT帯域・途切れ | 8k/16k、途切れ 0〜5% | HFP接続時の影響 |

### C. 議事録生成(LLM)の限界 — 主にL1(テキスト直接投入)

評価指標: 協議事項 再現率 / 適合率(でっち上げの有無)/ 状態正確性、アクションアイテム 再現率 / 担当 / 期限、**数値の転記正確性**、Stage2 JSON解析失敗回数、出力の途中切れ、生成時間。**各条件3回以上実行してばらつきを見る**(temperature 0.2でも結果が変わることが既に分かっているため)。

| No. | 試験 | 振る要因 | 知りたいこと |
| --- | --- | --- | --- |
| C-1 | 協議事項の数 | 5 / 10 / 20 / 30 / 40件 | Stage2 出力上限(`max_tokens: 4096`)で途切れる件数 |
| C-2 | 試験時間(文字数) | 文字起こし 1万 / 3万 / 6万 / 10万文字(3〜8時間相当) | `num_ctx: 32768` を超える時間、Stage2入力の上限 |
| C-3 | 文字起こしの誤り | 正解テキストに人工的な誤り CER 0 / 10 / 20 / 30 / 40% | STTがどこまで悪くなっても議事録が保てるか(A群とつなげて許容SNRを出す) |
| C-4 | 話者ラベルの誤り | ラベルを 0 / 10 / 30 / 50% 入れ替え | 担当(owner)と要求/回答の取り違えがどこから起きるか |
| C-5 | 状態の変化 | 変化回数 1〜4回、撤回・条件付き合意・保留 | 「合意済み優先」ルールが誤りになるケース(撤回された合意) |
| C-6 | 期限の表現 | 絶対日付 / 「来週金曜」「月末」「次回試験まで」/ 期限なし | 相対表現の扱い、年のでっち上げ |
| C-7 | 雑談・脱線 | 雑談比率 0 / 30 / 60% | 関係ない話が協議事項として出てこないか |
| C-8 | 題材の違い | S-TR / S-MT / S-PLC | 配電盤以外で性能が保てるか |
| C-9 | 否定・条件 | 「〜しないことで合意」「〜なら了承」 | 意味の取り違え |
| C-10 | 再現性 | 同一入力 × 5回 | run間のばらつきの大きさ |

### D. 処理性能・リソース — L1 + L2

| No. | 試験 | 内容 | 知りたいこと |
| --- | --- | --- | --- |
| D-1 | STT処理遅延 | チャンク受信から文字起こし送信までの時間(ログから算出)を条件別に | 画面表示の遅れ。騒音で処理が重くなるか |
| D-2 | 処理の追いつき限界 | 注入速度を 1.0 / 1.5 / 2.0 / 3.0 倍に | 何倍まで遅れずに処理できるか(=より遅いGPUでの余裕) |
| D-3 | VRAM逼迫 | 他プロセスで VRAM を 0 / 0.5 / 1 / 1.5 / 2 / 3 GB 占有してから試験 | ノートPCの画面表示分やROS2等と同居したときにどこでOOMになるか、その時の挙動 |
| D-4 | 生成時間のスケーリング | C-2 の各条件での生成時間 | 試験時間と生成待ち時間の関係 |
| D-5 | 連続運用 | コンテナを再起動せずに短時間試験を5回連続 | メモリ・VRAMの増加、状態の持ち越し |

### E. 異常系・運用 — L3

コードを読んで問題がありそうな箇所を先に挙げ、実際に起きるかを確認する。

| No. | 操作・障害 | 予想される問題(コード上の根拠) |
| --- | --- | --- |
| E-1 | コンテナを再起動せずに2回目の試験 | WebMヘッダーがプロセス全体で1つだけ保存され、リセットされない(`transcriber.py` の `_webm_header`)。これまでの試験は毎回再起動していたため表に出ていない可能性 |
| E-2 | 録音中にブラウザをリロード / 内蔵マイクWSが再接続 | 同上。新しいストリームの先頭に古いヘッダーが付く |
| E-3 | BTとinternalのエンコード条件が違う(サンプルレート等) | BT・internalで同じヘッダーを共有している |
| E-4 | 2つのセッションを同時に使う | `SpeakerDetector` がシングルトンで全セッション共有。リセットしても履歴・閾値が残る |
| E-5 | 録音中に「議事録を生成」を押す | 生成開始時にSTTモデルを解放するため、録音中のチャンクの文字起こしが失敗する可能性 |
| E-6 | 生成ボタンの二重押下 | 同時実行の排他がない |
| E-7 | 生成中にOllamaが停止 / 応答が300秒を超える | 例外で文字起こし済みデータが使えなくなるか、再生成できるか |
| E-8 | 試験中にコンテナが落ちる | 文字起こしがメモリ上にしかなく、全部失われる可能性 |
| E-9 | BTウィンドウを開き忘れる / 途中でBTが切れる | 全発話がclient、または直近のRMSに引きずられる |
| E-10 | 壊れたデータ・空データ・非常に大きいデータの送信 | ffmpeg失敗時の復帰 |
| E-11 | WebSocket切断の検知 | CHANGELOGに「切断を検知できない場合がある」と未解決で記録済み |
| E-12 | ダウンロードAPIに `../` を含むファイル名 | `download/{filename}` でパスを検証していない |

## 4. 合否の目安(限界点の定義)

「限界点」は、以下の目安を初めて下回る条件とする。目安そのものは実運用の要求が決まっていないため暫定値とし、結果を見て見直す。

| 指標 | 良好 | 許容 | 不可 |
| --- | --- | --- | --- |
| CER | ≤ 0.15 | ≤ 0.25 | > 0.25 |
| 数値・型式の正解率 | ≥ 0.95 | ≥ 0.85 | < 0.85 |
| 話者正解率 | ≥ 0.90 | ≥ 0.80 | < 0.80 |
| 協議事項 再現率 / 状態正確性 | ≥ 0.90 | ≥ 0.80 | < 0.80 |
| 協議事項 適合率(でっち上げなし) | ≥ 0.95 | ≥ 0.85 | < 0.85 |
| Stage2 解析失敗・出力途切れ | 0 | — | 1回でも発生 |
| 文字起こし表示の遅れ(p95) | ≤ 8秒 | ≤ 15秒 | > 15秒 |
| 異常系 | データ消失なし・復旧手段あり | — | 文字起こしが失われる / 復旧できない |

| `testing/results/v2/` | 条件ごとの結果と集計(限界点の表とグラフ) |

## 6. 進め方と所要時間の見積もり

| 段階 | 内容 | 目安 |
| --- | --- | --- |
| 0 | 環境確認(Docker・GPU・VOICEVOX起動)、現行版で `script_v1` を1回流して過去結果と一致するか確認(基準線) | 0.5日 |
| 1 | 試験ツール・台本・正解データの作成 | 1.5〜2日 |
| 2 | L3 異常系(短時間で終わり、重大な不具合が見つかると後の試験に影響するため先に実施) | 0.5日 |
| 3 | L1 掃引(A・B・C群) | 1〜1.5日(大半は放置で回る) |
| 4 | L2 E2E(限界付近の代表条件 8〜10run、各15〜30分) | 1日 |
| 5 | 結果のまとめ、改善の優先順位付け | 0.5日 |
| 6 | 改善の実装と、同じ試験での再評価(改善前後の比較) | 2〜3日 |

**改善候補(試験結果で優先度を決める。現時点の仮説)**
- WebMヘッダーをストリームごと・セッションごとに持つ(E-1〜E-3)
- `SpeakerDetector` をセッションごとにする(E-4)
- 録音中の生成を防ぐ、生成の二重実行を防ぐ(E-5、E-6)
- 文字起こしを随時ファイルへ保存し、コンテナが落ちても復元できるようにする(E-8)
- チャンク間のオーバーラップ(A-8・既知課題)
- Whisperへの専門用語ヒント(`initial_prompt` / `hotwords`)で数値・型式の誤りを減らす(A-7)
- 話者判定を「BTの絶対音量」ではなく「BTと内蔵マイクの音量比」で行う(B-1〜B-3)
- 協議事項が多い場合のStage2分割・出力上限の見直し(C-1、C-2)

## 7. この計画の範囲外・制約

- **実際のスピーカー再生→マイク収録(物理的な音響経路)は行わない**。劣化はすべてデジタルで模擬する。実機マイク・実際の工場騒音での確認は、別途現地で行う必要がある。
- 合成音声は人間の音声より発音が明瞭で、言い淀み・言い直しも台本どおりにしか入らないため、**実音声より精度が高く出る傾向がある**。結果は「上限側の目安」として扱う。
- 主観評価(議事録の読みやすさ等)は行わず、正解データとの照合で機械的に採点する。
